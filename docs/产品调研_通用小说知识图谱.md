> 基于剑来项目经验 + 业界现状的第一版参考报告。Agent 还在跑更深的调研，完成后会增补到 §附录。
> 作者：Claude | 日期：2026-04-22

## 零、TL;DR

- **市场状态**：有人做，但没人做好。英文向红海在作家端（NovelCrafter/Sudowrite），中文向**读者端几乎空白**。
- **技术成熟度**：核心技术栈（LLM + KG + 向量）已成熟。痛点集中在**共指消解、关系演化、成本**三点。
- **最大机会**：中文网文 × 读者端 × 移动端 × UGC 共建。剑来项目你已经验证了这条路的可行性。
- **最大风险**：版权合规、LLM 幻觉、百万字级单本成本。
- **一句话判断**：**NotebookLM 是最大半对标**——它证明了"上传文档+结构化问答"有用户需求，但它**不做持久结构化图谱、不做社交分享、不懂网文**。这就是你的窗口。

## 一、剑来项目经验蒸馏（通用化时要带走的）

### 1.1 可直接复用的模块

| 模块 | 核心价值 | 通用化改造点 |
|------|----------|--------------|
| `character_merger.py` — 别名解析（318条） | 降低重复合并 | 硬编码字典 → LLM 自学习 + 用户审核 |
| `relation_normalizer.py` — 12 类关系标准化（94.9% 边覆盖） | 关系语义收敛 | 12 类是"剑来向"，通用层需要扩到 20+ 类+题材子类 |
| `faction_normalizer.py` — 势力白名单 | 抑制幻觉 | 白名单从"人工维护" → 退化为"UGC 审核流" |
| `cultivation_normalizer.py` — 境界标准化 | 题材向 | 抽象成"等级/身份/职级"通用归一器 |
| 双端点容错（extract_pipeline.py） | 百万 token 可用 | 改为多供应商 Router（Gemini / Claude / DeepSeek / 通义） |
| 动态上下文注入 | 识别精度 +X% | **这是通用产品的核心**，必须先跑"主要人物识别"再正式提取 |
| `classify_quotes.py` — 金句情感分类（6类） | 差异化产品点 | 直接复用，金句 × 场景化卡片是流量抓手 |
| `build_graph_layout.py` — 关系图谱布局预计算 | 前端性能 | 通用产品复用 |
| `review_ugc.py` — UGC 审核流 + CDN 热更新 | 数据长期维护 | **这是你最稀缺的资产** |
| Taro 组件库 + 墨水风设计系统 | 移动端沉淀 | 直接复用 |

### 1.2 踩过的坑（反过来就是护城河）

1. **profiles_v3 内部 name ≠ 文件名**（Codex 发现的方法论错误）→ 任何一致性审计必须走内部字段
2. **链式别名陷阱**（火蟒→陈暖树，不能 火蟒→暖树→陈暖树）→ 别名图必须断环
3. **关系有方向性**（师徒→弟子需语义翻转）→ `get_reverse_types()` 已实现
4. **数据管道契约**（characters_lite 必须含 quotes/aliases）→ 需要契约测试而非靠记忆
5. **ScrollView/Canvas/Input 原生组件冲突**（小程序踩过）→ 条件 return 分支隔离
6. **CDN 热更新必须 --fail 校验**（curl 静默成功是大坑）

### 1.3 还没解决的通用问题

| 问题 | 现状 | 通用产品必须解决 |
|------|------|------------------|
| 关系演化时间轴 | 只存最终状态 | **两人 5 章敌对、500 章夫妻怎么表达** |
| 事件-人物-地点联动 | 有 events 字段但没闭环 | 时间线 UI 驱动的交互查询 |
| 跨章节共指消解 | 别名字典兜底 | 通用产品必须有自动 coref（BookCoref / LINK-KG 路线） |
| 增量更新 | 重跑整本 | LightRAG 路线：新章节 union 到已有图谱 |

## 二、业界技术栈调研

### 2.1 开源方案对比

| 方案 | 核心方法 | 适合长篇小说 | 成本（1MB 文本 ≈ 单本中篇） | 维护方 | License |
|------|----------|--------------|-----------------------------|--------|---------|
| **Microsoft GraphRAG** | 社区发现 + 多层抽象 | 中（原始 demo 用《绿野仙踪》） | **$5-20**，重度场景 $120/千页 | MSR | MIT |
| **LightRAG** | 双级检索 + 增量更新 | **高** | **$0.15**（vs GraphRAG $4-7，6000x token 效率） | 港大 HKUDS | MIT |
| **nano-graphrag** | GraphRAG 轻量社区实现 | 中 | ~$1 | 社区 | MIT |
| **BookNLP** | 专为书设计的传统 NLP pipeline | **高**（人物聚类、引语归属、事件 triple） | 本地免费 | UC Berkeley | Apache 2 |
| **LlamaIndex PropertyGraph** | 多抽取器可组合 | 中 | 变 | LlamaIndex | MIT |
| **Neo4j LLM Graph Builder** | LLM + Neo4j 可视化 | 中 | 变 | Neo4j | Apache 2 |
| **LangChain LLMGraphTransformer** | 三元组抽取 | 弱 | 变 | LangChain | MIT |
| **CREFT**（arxiv 2505.24553） | 多 Agent 序列专攻角色关系 | **专为此设计**（论文原型） | — | 学术 | — |
| **LINK-KG**（arxiv 2510.26486） | Coref-first KG | 专为此设计 | — | 学术 | — |
| **BookCoref**（arxiv 2507.12075） | 书级共指消解 | 专攻 coref | — | 学术 | — |

**关键结论**：
- **GraphRAG 成本太高**，不适合 C 端低价产品。一本 1000 页小说 ~$120 不可持续
- **LightRAG 是 2025 的新宠**：6000x token 效率 + 增量更新 = 完美匹配网文追更场景
- **BookNLP + LLM 混合** 是最务实的路径：BookNLP 做 NER+coref 粗处理（免费），LLM 做关系抽取（精处理），成本砍 80%
- **学术 2025 年扎堆做长篇共指**（BookCoref/CREFT/LINK-KG），可以直接借鉴方法论

### 2.2 直接对标产品

#### 英文向（作家端为主）

| 产品 | 定位 | 月费 | AI 能力 | 与我们的差异 |
|------|------|------|---------|--------------|
| **NovelCrafter** | 作家 + Codex 故事圣经 | $5-18 | 自带 + 外部 API | 写作辅助，不是读者分析 |
| **Sudowrite** | 作家 AI 辅助 | $19-59 | 强生成 | 生成为主，图谱为辅 |
| **World Anvil** | 世界观百科 | $4-23 | 弱 | 人工建图 |
| **Campfire Writing** | 模块化故事规划 | $25/年 + 模块 | 弱 | 纯 Planner |
| **Plottr** | 时间线 + 情节规划 | $25/年 | 弱 | 前期规划 |
| **Scribophile** | 写作社区 | $9.95 | 无 | UGC 评审 |
| **Shaxpir** | 文本分析 + 写作 | 未查证 | 传统 NLP | 学术向 |

> **观察**：英文市场全拥挤在"帮作家写"，没人做"帮读者读懂"。唯一半对标的是 NotebookLM（通用工具，非专业）。

#### 阅读辅助向（半对标）

| 产品 | 做什么 | 做小说？ |
|------|--------|----------|
| **NotebookLM** | 上传文档 + 问答 + 脑图 | **可用**，用户在 Royal Road 等论坛已实践，但通用工具、不持久、无社交 |
| **Matter / Readwise / Glasp** | 高亮 + 笔记同步 | 不做图谱 |
| **LitMaps** | 学术文献关系图 | 非小说 |

NotebookLM 的用户反馈（XDA Developers / Royal Road 论坛）揭示了真实需求：
- 想要"character arc 分析"
- 想要"两人关系是否合理"
- 想要"情节一致性检查"
- **但 NotebookLM 没有持久的人物卡、没有可分享的图谱、不理解网文语境**

#### 中文向（基本空白）

| 产品/方案 | 状态 |
|-----------|------|
| **起点中文网 / 阅文** | 只有书签、标签、评论；无自动人物图谱 |
| **番茄小说**（2025 MAU 2.45 亿） | 2025-11 严打 AI 批量低质内容；有作者助手，**无读者端图谱** |
| **微信读书** | 有 AI 问书（通用 RAG），非结构化图谱 |
| **笔灵 / 作家助手**（阅文官方） | 作家端，75% 网文作者已用 AI |
| **NRD Studio 人物关系图** | **手动输入**的在线编辑器 |
| **《红楼梦》可视化**（cnblogs 汀） | 单本手工项目，不成产品 |
| **剑来项目（你的）** | 读者端最佳实践之一 |

> **中文市场观察**：作家端已卷爆（笔灵等），读者端**完全空白**。中文网文独有的"境界/势力/金手指/CP"没有任何产品针对性处理。

## 三、差异化机会点（中文网文 + 读者端）

### 3.1 五种可落地产品形态

1. **「自动百科」**（最像你当前剑来）
   上传全本 → 完整图谱 → 详情页 + 分享卡
   - 壁垒：UGC 审核 + 粉丝共建 + 移动端体验

2. **「追书助手」**（LightRAG 路线）
   公众号/小程序订阅 → 新章节推送摘要 + 新人物提醒
   - 壁垒：增量更新成本

3. **「对比卡片社交」**（你已做人物 VS）
   扩展成"CP 对比卡"、"宗门对决卡"，一键分享小红书/抖音
   - 壁垒：模板 + 分发

4. **「金句引擎」**（你已有情感分类）
   Daily Quote + 情感搜索 + 场景化引用
   - 壁垒：情感分类质量

5. **「作家一致性助手」**（反做红海）
   给作家"你的第 500 章与前文人物设定是否矛盾"
   - 壁垒：作家付费能力高

### 3.2 中文网文特有需求（对标都没做）

- **境界/等级追踪**：主角从炼气到合体用了多少章？
- **势力层级图**：宗门 → 家族 → 国家 → 天下 的多层嵌套
- **金手指机制**：系统/穿越/重生的关键触发点与道具
- **CP 雷达**：女主候选 + 章节支持度曲线 + 读者投票
- **爽点密度**：章节热度曲线（为什么某 50 章大家都在追）
- **修仙体系可视化**：功法相克、法宝品阶、境界门槛

### 3.3 移动端机会

- 所有对标产品都是 Web/桌面
- 中文网文读者 70%+ 是移动端
- Taro 小程序 / 快应用借微信生态**零成本冷启动**
- 分享卡片天然适配微信 + 小红书

## 四、关键风险与对策

| 风险 | 严重度 | 对策 |
|------|--------|------|
| 版权合规（上传他人小说全文做商业图谱很灰） | 🔴 高 | ①只做"用户自读书" ②与阅文/番茄 API 合作 ③本地处理 + 云同步元数据 |
| LLM 幻觉（无法人工校审所有书） | 🟡 中 | ①UGC 审核流（你已有） ②置信度显示 ③多模型交叉验证 |
| 冷启动成本（单本 $0.15-$20 × N 本） | 🟡 中 | LightRAG + BookNLP 粗处理预筛 |
| 长尾维护（新章节谁来触发） | 🟡 中 | 订阅制 + 读者驱动 + 批量扫更 |
| 中文网文版权碎片（大平台独占） | 🔴 高 | 先做公版（红楼、金庸古龙）+ 用户本地书 |

## 五、建议的 MVP 路径

```
Phase 1 — 剑来通用化（4周）
  ├─ 抽离 generic 层：alias_resolver / relation_normalizer / extractor
  ├─ 去掉修真硬编码：cultivation_normalizer → optional plugin
  └─ 第二本测试：《凡人修仙传》或《红楼梦》（公版规避版权）

Phase 2 — LightRAG 重构数据管道（4周）
  ├─ 章节增量更新 union
  ├─ BookNLP 预处理（降本）
  └─ 成本目标：$0.1-0.5/本

Phase 3 — 读者端 MVP（4周）
  ├─ 小程序上传 .txt / 贴链接
  ├─ 自动图谱 + 每日金句 + 分享卡
  └─ UGC 审核沿用 review_ugc.py

Phase 4 — 差异化点（2周）
  ├─ 金手指追踪 / CP 雷达
  └─ 情感金句搜索
```

**总工期 14 周，单人可做到"给朋友看"的版本。**

我正在规划一款 C 端为主、B 端兼顾的「通用小说知识图谱」产品。用户上传任意小说文本（中文网文为主，兼顾英文、公版经典），系统自动提取：人物、关系、势力、地点、物品、事件、金句、时间线，输出交互式知识图谱 + 人物卡片 + 可分享内容。

## 调研目标
请交付 3000-5000 字中文 Markdown 报告，覆盖以下 9 维度。**每条事实必须给 URL**，不确定的标 `[需验证]`，**严禁编造**。

### A.2 中文网文生态补充

- **阅文"妙笔大模型"**（2023.7 发布）→ 作家助手妙笔版，阅文内部作家端 AI
- **番茄小说**：2024.5 上线 AI 写作 → 2025.4 因 AI 文爆量**开始收紧合同**（36氪报道）
- **七猫**：接入文心一言"AI 助手"
- **微信读书**："AI 问书" + AI 划线追问，无结构化图谱
- **Fandom（全球最大粉丝 wiki）**：2025 年仍**未推官方 AI 自动建图**——证明这个坑没人填

### A.3 版权合规关键点（⚠️ 重要）

- 2025 年 **国家版权局《网络文学 AI 生成版权保护指引》** 明确："二次创作 ≠ 合理使用"
- 保留原作人物设定 / 情节脉络**可能构成侵权**
- **合规方案**：
  1. 不存全文，只存结构化衍生数据 + 少量引文（合理使用比例）
  2. 与阅文 / 番茄走 API 合作授权
  3. UGC 免责声明
  4. 爬虫路线**慎重**
- 参考：[中国作家网 2025.5 AI 版权讨论](https://www.chinawriter.com.cn/n1/2025/0506/c404033-40474235.html)

### A.4 技术栈补充

- **LightRAG** 是 **EMNLP 2025 正式论文**，不只是社区工具（增加技术可信度）
- **LangChain LLMGraphTransformer** 实际上是 **Neo4j 贡献的**（走 Neo4j 技术栈更顺）
- **DeepKE（浙大）**：中文 KG 抽取三模式（有监督/少样本/LLM），中文网文场景可用

### A.5 商业模式观察

- **B/C 分层现实**：英文工具几乎全在作家端（付费意愿高），读者端无成熟付费模型
- "按本买断 / 传书式"（¥6-30/本）**是市场空白**，配合微信读书/起点会员体系可验证
- NovelCrafter 最低档 $4/月（比之前查到的 $5 更低，4 档阶梯更细）

### A.6 Agent 的一句话判断

> "通用小说 → 自动知识图谱"这件事：英文侧 **NovelCrafter/Sudowrite/NotebookLM 在写作辅助侧碰了边**，学术有 **BookNLP + GraphRAG/LightRAG** 把技术铺好了，但面向**中文网文读者、具备领域理解（境界/势力/金手指）、移动端优先、UGC 共建的成品——市场空白。剑来图谱就是 MVP 证明点。最大护城河：领域 Prompt + 中文网文语料 + 微信分发。最大不确定性：版权合规。**
