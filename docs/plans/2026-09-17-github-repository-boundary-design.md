# GitHub 仓库边界设计

## 结论

项目采用两个独立仓库：现有公开 `badDevBuild/jianlai` 保存完整 Taro 小程序；父目录项目保存为私有 `badDevBuild/jianlai-knowledge-graph`，负责数据管道、知识图谱、项目说明、设计文档和 JSON 样例。

## 为什么拆分

父项目与 `taro-app` 原本已经拥有独立 Git 历史，却误用了同一个远端地址。继续从两个目录向同一 `main` 推送会造成非快进冲突，强制推送还可能覆盖另一侧历史。拆分仓库可以保留既有小程序历史，同时让数据管道和内部项目资料独立演进。

## 上传范围

父项目允许上传：源码、数据处理脚本、项目说明、架构与产品设计、OpenSpec 记录、经过检查的 JSON 样例和发布数据。

部分 OpenSpec 记录描述可复用的通用小说知识图谱能力，并引用相邻的 `知识图谱项目/novel_kg` 实现。它们作为设计与迁移历史保留，不代表对应实现位于本仓库；执行相关任务前必须重新确认真实代码路径。

小程序允许上传：Taro 源码、页面与组件、样式、必要图标、分享卡片模板、公开小程序码、少量经过优化的客户端资源。

## 排除范围

两个仓库都禁止保存私钥、证书压缩包、Token、生产 `.env`、真实凭证、本机技能链接、构建缓存和重复生成物。2300 张法宝生成图继续通过资源服务器交付，不直接进入 Git；客户端只保存映射和必要的轻量回退资源。

## 发布流程

1. 对候选文件运行凭证扫描、JSON 解析和仓库状态检查。
2. 在各自仓库形成可审查提交。
3. 小程序构建通过后推送公开仓库。
4. 父项目推送私有仓库。
5. 推送后从 GitHub 重新读取分支提交号和可见性，确认远端状态。

## 回退

推送前保留原远端地址和本地提交号。若新私有仓库创建或推送失败，不修改现有公开仓库历史；修复后仅重试父仓库。小程序只允许快进推送，禁止用 `--force` 绕过冲突。
